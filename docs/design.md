# oauth2-mcp-gateway design

## 1. Sidecar boundary and scope

`oauth2-mcp-gateway` is a single-upstream OAuth 2.1 authentication sidecar for Model Context Protocol (MCP) servers. One gateway process binds a local socket behind an edge reverse proxy or tunnel (such as Nginx, Traefik, Caddy, Cloudflare Tunnel, or Tailscale Funnel) and fronts one MCP service.

In scope:

1. Serve OAuth 2.1 discovery metadata (RFC 9728 and RFC 8414), Dynamic Client Registration (RFC 7591), PKCE `S256` authorization code grants, single-tip generation-tracked refresh token rotation, and authenticated token revocation (RFC 7009).
2. Validate `Host` and normalized `Origin` headers, extract real client IPs from configured `trusted_proxies`, expose unauthenticated `GET` and `HEAD /healthz` probes (`200 OK`, `{"ok":true}` on `GET`), and verify opaque Bearer access tokens on `<resource_path>` (default `/mcp`) bound to `<public_url><resource_path>`.
3. Bridge authorized MCP traffic to an upstream Streamable HTTP MCP endpoint (with optional loopback-verified delegated authorization context) or to isolated per-session `stdio` child processes.
4. Stream configured unauthenticated capability URL prefixes (such as `/t/`) directly to an HTTP upstream origin without buffering bodies in memory.

Outside scope:

- TLS termination, ACME certificate management, HTTP/2 or HTTP/3 edge listeners, and multi-service virtual-host routing stay at the reverse proxy or tunnel.
- Persistent state lives in one local JSON file without external OIDC identity providers, SQL databases, or web administration UIs.
- MCP tool definitions, arguments, and results pass through without filtering or schema edits.

## 2. Configuration validation and state persistence

The gateway loads one JSON configuration file (capped at `1 MiB`) from `-c <path>`, `--config <path>`, or `OAUTH2_MCP_GATEWAY_CONFIG` (default `gateway.json`). Startup rejects unknown fields (`deny_unknown_fields`). Any string field equal to `"${VAR}"` expands from the process environment at startup, except entries in `upstream.args`, which pass verbatim as child command arguments. Partial interpolation (such as `"prefix-${VAR}"`) and unset or empty referenced variables fail startup.

Top-level fields:

- `listen`: local `IP:PORT` socket address to bind, such as `"127.0.0.1:8080"`.
- `public_url`: canonical external origin without path, query, fragment, or userinfo, such as `"https://mcp.example.com"`. Plain `http://` is permitted only when the host is `localhost`, `127.0.0.1`, or `[::1]`.
- `resource_path`: public MCP route served directly by the gateway, default `"/mcp"`. Segments must be non-empty ASCII letters, digits, or `-._~` without `.` or `..`, and cannot overlap `/oauth/`, `/.well-known/`, `/healthz/`, or any `passthrough_prefixes`. Changing `public_url` or `resource_path` invalidates existing resource-bound grants and requires clients to re-authorize.
- `state_path`: regular file path for persisted OAuth clients and hashed token grants (`state.json`), resolved relative to the config file directory when relative. On Unix, startup creates missing parent directories with mode `0700` and writes `state.json` with mode `0600` via a sibling temporary file, `fsync`, and atomic `rename`.
- `trusted_proxies`: optional list of reverse-proxy IP addresses or CIDR ranges trusted to supply forwarded client IP headers, default `[]`.
- `oauth`: owner credential and token lifetime configuration.
- `upstream`: tagged union (`"transport": "http"` or `"transport": "stdio"`).

`oauth` fields:

- `owner_password_hash` (`pbkdf2-sha256$<iterations>$<salt_b64>$<hash_b64>`, `600000` default iterations from `hash-password`, `10000..=5000000` accepted; `hash-password` reads all of `stdin` up to `4096` UTF-8 bytes and strips trailing `\r` and `\n` bytes before hashing) or `owner_password` (non-empty plaintext secret hashed in memory at startup with `PBKDF2-HMAC-SHA256` at `600000` iterations). Providing both or neither fails startup.
- `scopes`: non-empty list of whitespace-free RFC 6749 scope tokens, default `["mcp"]`.
- `allowed_redirect_hosts`: optional hostname allowlist for DCR `redirect_uris`, default `[]`. Loopback `http://` callbacks remain allowed; when non-empty, `https://` callbacks must match an IDNA-normalized entry in `allowed_redirect_hosts`. Wildcards and reserved OAuth response query parameters are rejected.
- `access_token_ttl_secs`: `60..=86400`, default `3600`.
- `refresh_token_ttl_secs`: `300..=7776000`, default `2592000` (30 days), at least `access_token_ttl_secs`.
- `max_grant_lifetime_secs`: cumulative sliding refresh ceiling per grant measured from initial authorization, default `3 * refresh_token_ttl_secs`, capped at `31536000` (365 days) and at least `refresh_token_ttl_secs`.
- `refresh_grace_secs`: `0..=86400` and `<= refresh_token_ttl_secs`, default `min(access_token_ttl_secs, refresh_token_ttl_secs)` (`3600` seconds by default).
- `refresh_reuse_policy`: `"converge"` (default) or `"revoke"`.
- `max_registered_clients`: `16..=4096`, default `512`.

`upstream` fields:

- `"transport": "http"`:
  - `url`: upstream MCP endpoint URL (`http://` or `https://`, without userinfo, query, or fragment).
  - `bearer_tokens`: optional pool of non-empty ASCII Bearer tokens, default `[]`. When non-empty, each OAuth grant pins the least-loaded slot at authorization time and sends `Authorization: Bearer <token>` upstream. When empty, client OAuth `Authorization` is stripped and no upstream `Authorization` header is sent.
  - `auth_context`: optional object configuring delegated client authorization propagation to downstream services such as `mcp-hookd`:
    - `check_listen`: loopback `IP:PORT` socket address (such as `"127.0.0.1:8083"`), distinct from `listen` with a non-zero port; non-loopback addresses fail startup.
    - `check_token`: shared Bearer secret of at least `16` visible ASCII bytes (`0x21..=0x7E`) required on `POST /authorization/check`.
  - `passthrough_prefixes`: optional path prefixes starting and ending with `/` (such as `["/t/"]`), default `[]`. Prefixes cannot overlap `<resource_path>`, `/oauth/`, `/.well-known/`, `/healthz/`, or the path of `upstream.url` (matched case-insensitively).
  - `request_timeout_secs`: `5..=3600`, default `300`.
- `"transport": "stdio"`:
  - `command`: executable path or name.
  - `args`: argument list passed verbatim, default `[]`.
  - `env`: explicit child environment variables, default `{}`.
  - `cwd`: optional child working directory.
  - `max_sessions`: `1..=256`, default `32`.
  - `session_idle_secs`: `30..=86400`, default `1800`.

## 3. Request guards, OAuth 2.1 endpoints, and refresh rotation

### 3.1 Host, Origin, client IP, and CORS discovery guards

- `HostPolicy` validates incoming `Host` authorities against `public_url` and blocks DNS rebinding requests. Loopback `Host` authorities (`localhost`, `127.0.0.1`, `[::1]`) are permitted only when `public_url` itself uses a loopback host; when `public_url` is an `https://` origin behind a local reverse proxy, `Host` must match `public_url` even if `listen` binds `127.0.0.1`.
- Real client IP extraction consults `trusted_proxies`: when `peer_addr.ip()` matches `trusted_proxies`, the gateway scans `X-Forwarded-For` from right to left and selects the first IP outside `trusted_proxies` (falling back to `X-Real-IP` or `peer_addr.ip()`). When `trusted_proxies` is empty or `peer_addr.ip()` is untrusted, forwarded IP headers are ignored.
- `Origin` validation compares normalized browser `Origin` headers against `public_url` across `<resource_path>`, `/oauth/*`, and `passthrough_prefixes`, returning `403 Forbidden` on mismatches while allowing non-browser clients that omit `Origin`.
- `/.well-known/*` routes answer `GET` and `OPTIONS` with read-only CORS headers so browser-based MCP clients can read discovery metadata prior to login.

### 3.2 OAuth 2.1 endpoints (`src/oauth.rs`)

1. `GET /.well-known/oauth-protected-resource` and `GET /.well-known/oauth-protected-resource<resource_path>` (RFC 9728):
   - Both routes publish `resource: "<public_url><resource_path>"` and `authorization_servers: ["<public_url>"]` so clients probing root or path-scoped discovery resolve the same resource URI.
2. `GET /.well-known/oauth-authorization-server` and `GET /.well-known/oauth-authorization-server<resource_path>` (RFC 8414):
   - Publish `issuer: "<public_url>"`, `authorization_endpoint`, `token_endpoint`, `registration_endpoint`, `revocation_endpoint`, `response_types_supported: ["code"]`, `response_modes_supported: ["query"]`, `grant_types_supported: ["authorization_code", "refresh_token"]`, `token_endpoint_auth_methods_supported: ["none", "client_secret_post", "client_secret_basic"]`, `code_challenge_methods_supported: ["S256"]`, and `authorization_response_iss_parameter_supported: true`. Other subpaths return `404`.
3. `POST /oauth/register` (RFC 7591):
   - Rejects `redirect_uri` entries that are relative, contain fragments or userinfo, carry reserved OAuth response query keys, use non-loopback `http://`, or fall outside `allowed_redirect_hosts`.
   - Applies RFC 7591 defaults (`grant_types: ["authorization_code", "refresh_token"]`, `response_types: ["code"]`, `token_endpoint_auth_method: "none"`), mints secrets for confidential clients (persisting only SHA-256 digests), and at `max_registered_clients` evicts only the oldest client with no active grants or authorization codes.
4. `GET /oauth/authorize` and `POST /oauth/authorize`:
   - Validate `client_id` and registered `redirect_uri` first (exact match, or RFC 8252 Section 7.3 dynamic non-zero port match when both registered and requested URIs use `http://127.0.0.1` or `http://[::1]` with the same literal loopback IP, exact path, and exact query, excluding `localhost`); unregistered `client_id` or mismatched `redirect_uri` values return `400 Bad Request` without redirecting. Once `client_id` and `redirect_uri` are verified, missing or invalid `code_challenge`, unsupported `code_challenge_method` (anything other than `S256` with a 43-character base64url challenge decoding to 32 bytes), unsupported `response_type`, invalid `scope`, or invalid RFC 8707 `resource` values redirect to `redirect_uri` with the corresponding OAuth error code, `iss=<public_url>`, and optional `state`.
   - Normalize optional RFC 8707 `resource` values (`<public_url>`, `<public_url>/`, or `<public_url><resource_path>`) to `<public_url><resource_path>`, rejecting other targets with `invalid_target`.
   - Seal each login form (`5` minute TTL) into a stateless form token encrypted with an `HMAC-SHA256` counter-mode keystream and authenticated with an Encrypt-then-MAC `HMAC-SHA256` tag (bound via AAD to `<public_url>` and the form `nonce_id`), paired with an `HttpOnly; SameSite=Lax` CSRF cookie: `__Host-mcp_ar_<id>` (`Secure; Path=/`) on `https://`, or `mcp_ar_<id>` (`Path=/oauth/authorize`) on loopback `http://`. Stateless form sealing allocates no server-side pending-form slot on `GET /oauth/authorize`, preventing unauthenticated form-flooding from blocking legitimate logins, while redeemed form nonces are recorded in bounded `consumed_auth_nonces` upon successful password verification to prevent single-form replay.
   - Serve a self-contained HTML login form with `AUTH_PAGE_CSP` (`Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'; form-action 'self'; frame-ancestors 'none'`), `X-Frame-Options: DENY`, and `Cache-Control: no-store`, showing client identity, callback URI, and requested scopes with `Authorize` and `Cancel`/`Deny` (`error=access_denied`) actions.
   - Run constant-time PBKDF2 password verification inside `spawn_blocking` under a bounded concurrency semaphore, rate-limiting failed attempts per resolved client IP (or via a short-window token bucket on untrusted loopback sockets when `trusted_proxies` is empty).
   - Issue a single-use authorization code (`5` minute TTL) bound to the exact per-request `redirect_uri` (including any dynamic loopback port) and redirect with `code`, `iss=<public_url>` (RFC 9207), and optional `state`.
5. `POST /oauth/token`:
   - `authorization_code`: consumes the single-use code (replaying a consumed code revokes the issued grant), authenticates confidential clients, verifies `redirect_uri`, `resource`, and `BASE64URL_NOPAD(SHA256(code_verifier)) == code_challenge`, pins the least-loaded `pool_slot`, assigns an opaque `aref_`-prefixed handle for `auth_context`, records initial authorization time for `max_grant_lifetime_secs`, persists SHA-256 digests of the access token and generation-0 refresh token, and sets `Cache-Control: no-store`.
   - `refresh_token`: rotates structured single-tip tokens (`rt1.<grant_id>.<gen>.<nonce>.<tag>`):
     - Rotating active generation `G` advances the tip to `G + 1`, clamps token lifetime by `refresh_token_ttl_secs` and the grant's `max_grant_lifetime_secs` deadline, persists SHA-256 digests of active `G + 1` and grace `G` in `state.json`, and caches the current tip response in memory until `grace_until`.
     - Parallel subagents presenting the grace token within `refresh_grace_secs` verify client credentials, resource, and scope, then receive the cached tip response so concurrent refreshes across multiple hops converge on one active tip.
     - Presenting an older family token after `refresh_grace_secs` follows `refresh_reuse_policy`: `"converge"` (default) verifies client credentials, resource, HMAC family lineage tag, and remaining grant lifetime, then returns the live tip response (rotating if the memory cache expired) so resumed parent or child agents keep sibling sessions alive; `"revoke"` enforces RFC 9700 reuse detection, revokes the grant, cancels its gateway HTTP response streams, and terminates its `stdio` children.
6. `POST /oauth/revoke` (RFC 7009):
   - Authenticates the caller (`client_id` matching the grant for public clients, or `client_secret_basic` / `client_secret_post` for confidential clients), revokes any matching grant, cancels its gateway HTTP response streams, terminates its `stdio` children, and returns `200 OK`. Upstream HTTP session deletion is best effort.

OAuth `POST` endpoints cap request bodies at `64 KiB` with a `10` second read timeout.

### 3.3 Bearer challenges on `<resource_path>`

- Requests without an `Authorization` header (or without a `Bearer` credential) fail before reading the request body with `401 Unauthorized`, `Connection: close`, and `WWW-Authenticate: Bearer resource_metadata="<public_url>/.well-known/oauth-protected-resource<resource_path>"`.
- Requests carrying a malformed, unknown, expired, resource-mismatched, or revoked Bearer token return `401 Unauthorized`, `Connection: close`, and `WWW-Authenticate: Bearer error="invalid_token", resource_metadata="<public_url>/.well-known/oauth-protected-resource<resource_path>"`.
- Requests rejected for insufficient OAuth scope return `403 Forbidden` with `WWW-Authenticate: Bearer error="insufficient_scope", resource_metadata="<public_url>/.well-known/oauth-protected-resource<resource_path>"` (plus `, scope="<required_scopes>"` when downstream provides valid RFC 6749 scope tokens).

## 4. Active byte budget and upstream transport semantics

### 4.1 Process active byte budget (`src/types.rs`)

- One process-wide `ByteBudget` (default `1 GiB`, configurable in tests) accounts for owned MCP request buffers, decoded request text and keys, retained request identifiers, encoded stdin lines, notification encodings, HTTP SSE priming buffers, and all buffered `stdio` response lines. These leases measure payload allocation capacity; allocator overhead, `Value` container metadata, and total process RSS sit outside this counter.
- Passing a buffer from the `stdio` line reader into downstream HTTP streaming transfers its `ByteLease` in place so one buffer is charged once, while independent concurrent buffers sum against the shared budget.
- Every initial reservation and buffer growth uses non-blocking `try_acquire` / `try_reserve` and charges allocated buffer capacity. Growth reserves the old capacity plus the replacement capacity before allocation and copying. When the doubled-capacity peak exceeds the available budget, growth falls back to reserving the exact required capacity. The old buffer is freed before reducing the lease to the replacement's actual capacity. Checked-arithmetic, budget, or allocation failure leaves the original buffer and lease intact for caller cleanup without waiting for memory. First allocation and reuse within existing capacity need no duplicate charge.
- Both MCP ingress paths accumulate request frames directly into a capacity-leased `Vec` without collecting separate chunk buffers first. HTTP forwarding transfers that allocation into a `Bytes` owner; cloning or slicing it retains the lease until the final user releases it. The `16 MiB` limit and `30` second body-read deadline apply on ingress; budget rejection returns `503` with `Connection: close`. Empty GET/DELETE bodies need no positive reservation.
- Stdio parsing reserves an additional `3R` bytes for a body of length `R`: decoded text fits in `R`, and the JSON parser's escaped-string scratch has a `2R` growth allowance. The raw body has its own lease and is freed after parsing. The parsed value then retains only its measured string/key capacities. Rewritten values and retained ID/progress-token copies are admitted before cloning; encoding counts the exact JSON length before allocating, including the stdin newline. The stdin queue and writer own the resulting leased `Bytes`, independently of the caller's lifetime.
- Each waiter preallocates a correlated error buffer sized by its encoded client ID plus `256` bytes for the fixed error fields and messages. This buffer also supplies the temporary ID encoding during large-response rewriting. Budget failure can therefore still deliver the original ID without allocating an uncharged replacement. Normal completion or cancellation frees the unused buffer; an error transfers its lease into the downstream frame. Locally generated disconnect/timeout cancellation keeps its bounded stdin control path.
- `LeasedFrameCursor` and `SsePrimingFilterBody` transfer their buffers and leases into `Bytes` ownership. Output frames share that allocation in slices of at most `64 KiB`; the lease remains charged until the cursor and every returned frame release it. Static SSE prefixes and suffixes use separate frames. A reply is wrapped in this body owner before awaiting child cleanup, so cancellation drops the payload before its lease, including when the cleanup future has not been polled.

Budget tests leave `40,000` additional bytes available while the original response remains charged, and reject a `40,001`-byte replacement while retaining the original ID. Small chunked request, stdout, and SSE tests check the old-plus-new allocation peak at one byte below, exactly at, and one byte above admission. A separate normal forwarding test includes both response allocations, the concurrent request, retained identifiers, and error workspace in the process pool, checks ID and explicit-null preservation, and requires the final active charge to return to zero.

### 4.2 HTTP upstream (`src/upstream_http.rs`)

- Authorized `<resource_path>` calls read JSON-RPC request bodies up to `16 MiB` (`30` second read timeout) before forwarding, and stream upstream JSON and SSE response bodies without a response size limit. `https://` upstreams enforce `.https_only()` with OS native TLS root certificates.
- Forwarded calls on both `<resource_path>` and `passthrough_prefixes` unconditionally strip hop-by-hop headers, client OAuth `Authorization`, `Origin`, `Cookie`, `Forwarded`, `X-Forwarded-*`, `X-Real-IP`, `X-Remote-User`, `X-Original-URL`, `X-Rewrite-URL`, `CF-Connecting-IP`, `True-Client-IP`, `X-User-*`, and `X-Authorization-*` headers, strip upstream `Set-Cookie`, set `X-Forwarded-Proto` from `public_url`, and add `X-Accel-Buffering: no`. On `<resource_path>`, the gateway injects `Authorization: Bearer <bearer_tokens[grant.pool_slot]>` when pooled tokens are configured.
- Delegated authorization (`upstream.auth_context`):
  - When `auth_context` is configured, authorized `<resource_path>` requests inject `X-Authorization-Ref: <aref>` (the grant's opaque `aref_`-prefixed identifier) and `X-Authorization-Scope: <space-separated scopes>` after stripping any client-supplied `X-Authorization-*` headers. `passthrough_prefixes` remain unauthenticated capability routes and never receive `Authorization` or `X-Authorization-*`.
  - A dedicated loopback HTTP/1.1 listener on `auth_context.check_listen` serves `POST /authorization/check`. It verifies `Authorization: Bearer <check_token>` in constant time, rejects requests carrying `Origin`, reads bounded JSON `{"ref": "aref_..."}` payloads, and replies `200 OK` with `{"active": true, "principal": "<aref>", "resource": "<public_url><resource_path>", "scopes": [...], "expiresAt": <unix_secs>}` for live grants or `{"active": false}` for unknown, expired, or revoked grants.
- Upstream `401` / `403` status and `WWW-Authenticate` handling:
  - Without `auth_context`, any upstream `401` or `403` when `bearer_tokens` is non-empty indicates a failed static upstream credential and maps to an empty `502 Bad Gateway`, and upstream `WWW-Authenticate` headers on `<resource_path>` are stripped.
  - With `auth_context` enabled, downstream services distinguish hop-token failures from delegated client authorization rejections via `WWW-Authenticate`:
    - Upstream `401 Unauthorized` carrying `WWW-Authenticate: Bearer ... error="invalid_token"` preserves `401` (and any valid JSON error body) and rewrites `WWW-Authenticate` with the gateway's own public `resource_metadata` URL (`Bearer error="invalid_token", resource_metadata="<public_url>/.well-known/oauth-protected-resource<resource_path>"`).
    - Upstream `403 Forbidden` carrying `WWW-Authenticate: Bearer ... error="insufficient_scope"` preserves `403` (and any valid JSON error body) and synthesizes `WWW-Authenticate` using `error="insufficient_scope"`, the gateway's public `resource_metadata` URL, and any validated RFC 6749 `scope="..."` attribute from the upstream challenge.
    - Upstream `401` responses without a valid delegated `invalid_token` challenge and `403` responses with a non-delegated Bearer challenge map to an empty `502 Bad Gateway`. A `403` without `WWW-Authenticate` remains `403`, preserving ordinary upstream permission errors. Internal upstream realms and metadata URLs never pass raw to clients.
- Session bindings cap at `32` `Mcp-Session-Id` entries per `grant_id` and `4096` across the process. Each `SessionBinding` carries a monotonic `binding_id`, `last_used_seq`, `active_post_streams`, and a per-session `CancellationToken`:
  - Request lookup records `req_binding_id` under the state lock, and response handling checks `binding_id == req_binding_id` so late `404`, `200`, or `DELETE` responses from an evicted or deleted generation never remove, cancel, or stream onto a newly rebound session sharing the same `Mcp-Session-Id`. When request and response headers carry the same session ID, session metadata updates in place without re-running new-session binding.
  - `DELETE <resource_path>` removes the bound session and fires its `CancellationToken` only when the upstream responds with `2xx` or `404 Not Found`; upstream `405 Method Not Allowed` or `5xx` responses keep the session binding and active `GET` SSE streams open. Non-`DELETE` requests remove the session binding when the upstream responds with `404 Not Found`.
  - `POST` calls increment `active_post_streams` from pre-flight lookup (or new-session response bind) until `GrantBoundBody` finishes streaming the response, refreshing `last_used_seq` when a `POST` stream completes. Background `GET` SSE listener streams leave `active_post_streams` and `last_used_seq` untouched and select on the per-session `CancellationToken`, closing as soon as the session is evicted, deleted, or revoked.
  - Capacity eviction chooses only among `active_post_streams == 0` bindings with the lowest `last_used_seq`, cancels the victim's session token, and sends an upstream `DELETE`. When every slot at the per-grant or global limit has `active_post_streams > 0`, the gateway preserves running calls, dispatches an upstream `DELETE` to clean up the newly minted `Mcp-Session-Id`, and returns `503 Service Unavailable`.
- For `Content-Type: text/event-stream` responses with no `Content-Encoding` or only `identity` encodings, `SsePrimingFilterBody` consumes one leading UTF-8 BOM and drops leading SSE blocks without a `data` field (such as bare `retry:` directives or comment keepalives). It enforces the `1 MiB` per-stream priming cap and acquires `ByteBudget` capacity before buffering bytes. Non-identity encodings pass through with their original bytes and `Content-Encoding`; `GrantBoundBody` still handles grant/session cancellation and stream timeouts.
- Grant revocation (`POST /oauth/revoke` or post-grace replay under `"revoke"`) bumps the grant epoch, cancels active response streams for that grant, and sends best-effort upstream `DELETE` requests for its bound sessions. A refused or failed deletion leaves remote cleanup to the upstream's own session lifecycle.
- `passthrough_prefixes` routes reject path traversal (`..`, `\`, NUL bytes, control bytes, and multi-round percent-encoded dot segments), validate `Origin` when present, strip sensitive headers (including `X-Authorization-*`), and stream `GET`, `HEAD`, and `PUT` bodies directly without buffering in memory.

### 4.3 Stdio upstream (`src/upstream_stdio.rs`)

- Spawned children start with `env_clear()`, receiving a minimal OS runtime variable allowlist plus `upstream.env`. On Unix, each child enters a dedicated `setsid` process group; during termination the gateway closes `stdin`, keeps the group leader unreaped via `waitid(..., WNOWAIT)` across `200 ms` grace wait, sends `SIGTERM` (`2 s` wait) and `SIGKILL` to `-pid`, and reaps the leader last so the kernel cannot recycle the PGID mid-signal. On Windows, each child starts with `CREATE_SUSPENDED`, attaches to a Job Object configured with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, and only then resumes (compatible with nested jobs without `CREATE_BREAKAWAY_FROM_JOB`). Assignment or resume failures transfer the job, child, and slot into the tracked reaper before awaiting cleanup. Caller cancellation cannot release that slot early, and shutdown waits for pending spawn reservations and reapers.
- In-session `POST <resource_path>` lookup validates `grant_id` and child liveness, updates `(last_client_active_ms, last_client_seq)`, and increments `active_requests` (`ActiveRequestClaim`) atomically under one session table lock, handing that count directly to notification write or `RequestGuard` so concurrent GC never sees `active_requests == 0` mid-dispatch.
- Wire framing rewrites JSON-RPC `id`, cancellation `requestId`, `_meta.relatedRequestId`, and `_meta.progressToken` per call and restores the caller's identifiers on matching notifications and responses. The stdout reader replies to child `ping` requests and returns method-not-found errors for unsupported server-to-client requests so children do not block; client disconnects write `notifications/cancelled` with the mapped wire `requestId` to child `stdin`. A cancellation whose client ID no longer matches an active request is accepted without forwarding, so a late cancellation cannot stop another wire request.
- MCP Events over `stdio`:
  - `events/stream` calls (both in-session and sessionless) require `Accept: text/event-stream` (`q > 0`), returning `406 Not Acceptable` with JSON-RPC `-32600` before slot acquisition or dispatch when absent.
  - Each `events/stream` request maps the caller's JSON-RPC `id` to its numeric `wire_id`. Push notifications (`notifications/events/active`, `notifications/events/event`, `notifications/events/heartbeat`, `notifications/events/error`, and `notifications/events/terminated`) match `params._meta["io.modelcontextprotocol/subscriptionId"] == wire_id`, rewrite that `subscriptionId` back to the caller's original JSON-RPC `id`, and route exclusively to that `events/stream` SSE response body. Valid `events/stream` completion responses likewise restore both `result._meta["io.modelcontextprotocol/subscriptionId"]` and top-level `id`. Push notifications missing a matching numeric `subscriptionId` are ignored, and notification-queue or byte-budget overflow closes the affected stream cleanly.
  - Unscoped `notifications/events/list_changed` notifications from the child follow the session notification path and forward over active SSE response streams within the `4 MiB` per-session notification queue cap.
- Sessionless modern requests and discovery:
  - Requests carrying a modern `MCP-Protocol-Version` header or `params._meta["io.modelcontextprotocol/protocolVersion"]`, and valid `server/discover` calls without `Mcp-Session-Id`, run directly on an ephemeral child managed by `EphemeralGuard`. The child receives the original method, parameters, and per-request client metadata. It is reaped when the response finishes or the caller disconnects.
  - `server/discover` returns the child's own result or error without synthesizing capabilities, versions, or server information. Modern servers need no `initialize` exchange. Legacy clients retain the separate stateful `initialize` path, and clients can use a legacy server's discovery error to choose that path. These lifecycles follow [MCP versioning and compatibility](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning).
  - A sessionless notification waits up to `30 s` for its FIFO stdin line to complete `write_all` and `flush`, then reaps the child before returning `202`. The receipt confirms pipe delivery; application processing remains asynchronous. A failed write or closed receipt returns `502`, and a write timeout returns `504`, after tracked cleanup. Queue or byte-budget rejection returns `503`. The queued or writing line retains its leased bytes until completion or cancellation.
- Slot accounting keeps `sessions.len() + reserved_slots + terminating_slots <= max_sessions` at all times:
  - `EphemeralGuard` owns the `SlotReservation` from child spawn until table commit; on early exit, SSE stream completion, or caller TCP disconnect, `SlotReservation::into_terminating` atomically shifts the slot from `reserved_slots` to `terminating_slots` and runs process-group termination inside a tracked background task before releasing the slot and waking `slot_notify` waiters.
  - Client idle tracking updates `(last_client_active_ms, last_client_seq)` only on `initialize` table commit, valid in-session requests or notifications, normal request completion, and downstream SSE frame consumption. Unsolicited child `stdout` output and disconnect cancellations do not refresh client activity.
  - `acquire_slot` runs three steps under the session table lock: (1) reserve immediately when `used_slots() < max_sessions`; (2) reap all dead (`!alive`) or `session_idle_secs`-expired idle sessions across all grants, transferring one freed slot directly to the caller and placing any remaining victims in `terminating_slots`; (3) if still full, evict the single session matching the caller's `grant_id` with `alive == true`, `active_requests == 0`, client idle duration `>= pressure_idle` (default `600` seconds, capped by `session_idle_secs`), and minimal `(last_client_active_ms, last_client_seq)`, transferring its slot before reaping outside the lock. If no victim qualifies while `terminating_slots > 0`, the caller waits (up to `INIT_TIMEOUT`) for reaping to free a slot; otherwise admission returns `503 "session limit reached"`.
- Inbound JSON-RPC bodies cap at `16 MiB`. Child `stdout` framing separates control messages from tool responses:
  - Every stdout line reserves capacity before its first append, with the raw buffer and lease in one owner through partial reads, cancellation, parsing, and dispatch. Completed small lines reserve the same `3R` parsing workspace as ingress requests, then retain measured text/key capacity. Child `ping` and method-not-found replies borrow the child ID and count their encoding before allocating; queued lines and pending sends own the resulting leased bytes. Budget rejection uses the explicit waiter error and child cleanup path.
  - Lines within `1 MiB` parse normally; per-session queued SSE notification copies share a `4 MiB` budget charged by each copy's allocated string capacity and drop excess notifications when full. Each encoding also owns a process-budget lease. Dequeue adds the SSE prefix and suffix in the same allocation after any required non-blocking growth; its process lease follows the returned frame. Dropping the queue entry releases the separate session-queue charge, so that `4 MiB` queue budget does not cover frames already handed downstream.
  - Lines exceeding `1 MiB` continue buffering up to `512 MiB` only when at least one call is in flight and `ByteBudget` grants a non-blocking lease. A streaming top-level JSON scanner (tracking string escapes and brace depth `1`) locates `"method"` and the exact byte span of top-level `"id"`; completed large responses validate strict JSON syntax via zero-AST `serde::de::IgnoredAny` and splice the client `id` directly into the leased `Vec<u8>`.
  - Completed large responses retain their allocated capacity after ID rewriting and transfer its lease into downstream frames. They release that capacity when the final frame owner drops, without a separate shrinking allocation.
  - Any rejection before consuming the line's trailing `\n` (exceeding `512 MiB`, scanning top-level `"method"` past `1 MiB`, output past `1 MiB` with no active request, or exhausting `ByteBudget`) terminates the session and delivers the explicit error status and reason to all waiting JSON and SSE callers. Complete oversized `"method"` lines or unmatched response IDs are discarded in place while keeping the session open.
